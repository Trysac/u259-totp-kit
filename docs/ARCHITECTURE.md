# Architecture

## Design Decision: Recovery Code Generation

Recovery codes are generated by interpreting five random bytes as a big-endian integer and converting to lowercase base32 (8 characters), then formatting as `xxxx-xxxx`. This matches the acceptance example `bytes([1]*5)` → `aeaq-caib`. The alternative of using standard `base64.b32encode` (bit-level encoding) would produce `aeaeaeae`, which does not match the specification's test vector.

Recovery-code storage does **not** use a fast unsalted hash. The 40-bit code space is small enough that a single SHA-256 digest can be enumerated offline in minutes and, with no salt, a precomputed table can be reused for every user. Instead, each entry is a self-contained `salt || scrypt` value: a random 16-byte per-entry salt followed by a 16-byte tag from `hashlib.scrypt(n=2**14, r=8, p=1)`, hex-encoded to the existing 64-character shape. `to_json()` therefore never contains a plaintext code or a cheap digest of one. Callers may additionally pass a server-side `pepper` to `from_codes`/`from_json`; the pepper is held outside the datastore and mixed in with HMAC-SHA-256. The small code space still requires application-level attempt limits and access controls on backups, but a leaked serialized set no longer makes offline recovery of every code practical.
